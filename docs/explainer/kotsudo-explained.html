Kotsudo Explained

How the Maya → Unreal Engine 5.6 rigging pipeline rebuilds each rig feature: the logic, the problems we hit, and how we solved them. Test character: Murakami.

Every feature follows the same five parts: what it is in Maya, the challenges, how we solved it (with a visual beside each solution), how we know it works, and its limits.

Maya side Unreal side A problem, or an old behaviour we replaced

The idea behind it all

The tool never asks "is there a node called X?". It asks "what moves what, and by how much?", writes the answer down in neutral terms, and lets Unreal rebuild it with its own tools.

  1. Read the evidenceLook at what the scene actually does, not at node names.
  2. Describe intentUnreal axes, centimetres, linear colours, maths steps. Not a list of Maya nodes.
  3. Rebuild nativelyUse Unreal's own Control Rig nodes and assets.
  4. Measure parityEach feature has a test comparing our description with what Maya computes.
  5. Never guess silentlyAnything we cannot describe is reported with its reason.

The shared walker: slider → maths → target

Three of the four features below rest on one piece of code. In Maya, a value is often computed from a slider through a chain of utility nodes (multiply, reverse, condition, driven keys and so on). The walker starts at the value and walks backwards to the slider, writing each step down as a simple operation. Unreal rebuilds that list with its float nodes. The same walker serves blendshape weights, space weights and driven groups.

Space switching

A controller follows a different thing depending on a choice: a hand that follows the World, the Chest or the Head.

Maya: testedOffline: testedUnreal: not run yetMurakami has none; tested on a synthetic rig

What it is in Maya

Riggers build it with three pieces:

  • an empty group above the controller (here hand_space_grp);
  • a constraint on that group, with one target per space;
  • a choice attribute on the controller, usually an enum called "Space", that turns one target's weight on and the others off.

A weight is how much a target pulls on the group: 1 means "follow it fully", 0 means "ignore it".

The challenges

  1. Every rigger wires it differently. Weights can be switched by condition nodes, driven keys, reverse nodes, separate float sliders, choice nodes or matrix nodes. Recognising one specific setup only works on rigs built that way.
  2. The wiring goes through the constraint itself. Maya adds a weight attribute on the constraint (chest_ctrlW1) that feeds the target slot. Our walker first stopped there and took the constraint for the controller.
  3. Targets aren't always controllers. A space can be a joint, a locator hidden under a joint, or a locator in the world.
  4. Each space has its own offset. Maya stores one offset per target, and they don't have to agree. On Murakami's toe, switching IK → FK moves it 1.011 cm in Maya itself. Unreal's "maintain offset" only remembers one.
  5. Not every space is a full parent space. Some take only the rotation (orient: "the head keeps looking where the body points") or only the position (point).
  6. Murakami has no space switch, so it couldn't be the test.

How we solved it

SOLUTION 1

Describe the weights as maths, not as nodes

For each target, the walker follows the weight back to the slider and writes the steps. A condition node becomes a comparison step ("1 if Space = 2, else 0"). Driven keys become their key list. Any wiring made of these steps works, in any combination.

Try it: pick a space, then bend the chest or turn the head. The hand follows only the thing its active space points to.

SOLUTION 2

Walk through the constraint's own weight attributes

When the walk lands on one of the constraint's attributes, it keeps going upstream until it reaches a real controller. A weight attribute that nothing drives counts as a constant.

SOLUTION 3

Say what each target follows

Unreal doesn't know Maya's locators. For each target we record the nearest exported thing it moves with: the nearest controller above it, else the nearest exported joint, else the world.

SOLUTION 4

Measure each space alone, in Maya

We don't predict per-space offsets. We measure them. The exporter tries values for the slider and reads Maya's actual constraint weights each time. When exactly one target is active, it records where the controller sits.

The values tried come from the enum's entries, the slider's limits, and the numbers that appear in the maths. It also records which value selects which space, and the enum labels, including enums with explicit values like Low=0:High=10.

SOLUTION 5

Rebuild it in Unreal with one null per space

A null is an invisible transform in the Control Rig. The builder makes:

  • one null per space, hung under its target and placed where Maya puts the controller under that space alone;
  • the matching Unreal constraint: Parent, Rotation or Position;
  • weights computed live from the enum channel with the shared float nodes. Comparisons use Unreal's compare and select nodes, with a pure-arithmetic fallback.

Because each null already sits at its measured pose, each space keeps its own offset. That answers challenge 4.

SOLUTION 6

Orient and point spaces keep the other half

For a rotation-only or position-only space, the space null hangs under the controller's real Maya parent. The constraint then only overrides one half, and the other half still follows the parent.

SOLUTION 7

No silent guess

Before, an undescribable space quietly fell back to "follow the joint nearest to the targets". Now the reason is written down ("driven by several constraints", "matrix network", "unsupported weight wiring") and shown in the Checks tab, the Setup rows and the Unreal log. The fallback still exists, but it's labelled.

SOLUTION 8

The pose check probes every space

An enum is now probed on every value, not just its maximum. Testing only the maximum would skip the middle spaces.

How we know it works

A test rig (tests/maya_space_switch_test.py) with the common setups:

  • an enum through condition nodes, with world, controller and joint targets, and one offset edited on purpose;
  • an enum through driven keys;
  • an orient-only float slider with a reverse node;
  • a matrix-driven space.

For every value, the exported weights equal Maya's. The edited offset is measured at exactly 2.0, and the matrix case is reported instead of guessed. On Murakami, the toe's IK/FK blend is now recognised as a two-space switch ("IK = L_LegIKctrl, FK = L_LegFKctrl_03").

Limits

  • Matrix-based spaces (offsetParentMatrix, blendMatrix) are reported, not rebuilt.
  • So are groups driven by several constraints at once.
  • "Switch without jumping" (snapping the controller so it stays in place when you change space) is an animation tool and isn't built yet.

Offset / zero groups

The empty groups above a controller. Some just hold the rest position. Others are moved by sliders, like Murakami's petals.

Maya: tested (0.0001 cm)Offline: testedUnreal: not run yet

What it is in Maya

Above almost every controller sit one or more empty groups (_grp, _offset, _zero…).

  • Zero groups hold the rest position, so the controller's own channels read 0 at rest. The animator can always zero a controller to get back to rest.
  • Driven groups are moved by something else: driven keys, an "auto" behaviour, or a settings slider.

On Murakami, the 12 pedal_NULLctrl_* groups are moved by Petal_Translate and Petal_Rotation on Head_Settings_Ctrl.

The challenges

  1. Telling the kinds apart. A group can be static, constraint-driven (that's a space), slider-driven, or placed by matrix nodes. Each needs a different answer.
  2. Unreal has no "group" between a parent and a control. It has an equivalent for static groups (solution 2), but not for moving ones.
  3. Rebuilding a moving group exactly means reproducing how Maya builds a local transform: translate, the rotate axis, the rotation in the group's rotate order (xyz, zxy…), and the joint orient when the group is a joint. All of it converted from Maya's axes to Unreal's.
  4. Static groups above the moving one still have to count, even though Unreal doesn't create them.
  5. A hidden unit trap. Maya stores rotations in radians and distances in centimetres internally, but shows degrees and scene units (metres on Murakami). The unit-conversion nodes Maya inserts work in the internal units.
  6. The slider's controller belongs to no module. Head_Settings_Ctrl isn't in any tagged module, so Unreal never built it, and its sliders didn't exist.

How we solved it

SOLUTION 1

Record and classify each controller's group stack

Each controller records the groups between it and its parent controller, nearest first. Each group gets one of four labels, and each label has its own treatment.

SOLUTION 2

Static groups = the Unreal control's offset

An Unreal control has an "offset transform" separate from its animatable value. That is exactly a zero group. The builder puts the full rest transform into the offset, so the control's channels read 0 at rest.

No extra null is needed. This part already worked; now it's identified and documented.

SOLUTION 3

Driven groups become real nulls, rebuilt every frame

A null is inserted between the parent and the controller. Every frame its local transform is rebuilt as L(channel values) ∘ C, read "apply C, then L":

  • L is Maya's own local-transform formula, fed with the current channel values.
  • C is a constant computed once at build time (solution 5).
  • The driven channels come from the sliders through the shared walker maths. The other channels keep their rest values.

Try the two petal sliders. The numbers on the right are what the null receives.

SOLUTION 4

L follows Maya's order, and the rotate order matters

Maya builds a local transform in a fixed sequence: rotateAxis, then the rotation in the group's rotate order, then jointOrient (joints only), then translate. We build L in that same sequence.

The rotate order is easy to underestimate. The same three angles give a different result in a different order, as the two gizmos show. Change the angles or the orders.

SOLUTION 5

Convert axes, and flip the angle sign

Maya is Y-up; Unreal is Z-up. A Maya vector (X, Y, Z) becomes (X, Z, Y) in Unreal. Swapping two axes is a mirror: Maya is right-handed and Unreal is left-handed.

A mirror reverses what "positive rotation" means. So a rotation by θ about a Maya axis becomes a rotation by −θ about the matching Unreal axis. Same physical turn, opposite sign.

SOLUTION 6

The constant C absorbs everything that doesn't move

C is computed once at build time. It absorbs the static groups above the driven one, and the difference between Maya's parent and the Unreal parent. It is chosen so that, with the rest values, the null lands exactly where Maya's group is.

For the curious: C = L(rest)⁻¹ ∘ G_rest ∘ U_rest⁻¹, where G is the group's world pose in Maya and U the Unreal parent's.

SOLUTION 7

One unit rule, applied everywhere

The maths always goes from the value the animator sees on the slider to the value the animator sees on the target. In those terms, Maya's hidden unit conversions between a plain number and an angle or distance do nothing, so we count them as "× 1".

Our walker first got this right only for plain numbers like blendshape weights. For a rotate channel it would have produced radians.

SOLUTION 8

Settings controllers are built on first use

The exporter finds controllers whose sliders drive exported things but which belong to no module, and writes them as settings_controls. Unreal builds such a controller the first time a driven group or blendshape needs its slider, under its real Maya parent.

SOLUTION 9

One entry point for every module

The groups are inserted inside the one function every module already uses to find a control's parent. FK, IK/FK, spline and constraint controls all get them, without touching each module.

How we know it works

  • Against Maya's own world matrices (tests/maya_driven_groups_test.py): driven groups with random rotate orders and rotate axes, a driven joint with jointOrient, under randomly rotated static groups, in centimetre and metre scenes. The predicted world pose matches Maya's within 0.0001 cm and 0.0001°.
  • The Unreal graph, evaluated offline (tests/offline_driven_groups_test.py): the quaternion, vector and float nodes, evaluated with numbers, give the same result as the Maya-checked maths.
  • On Murakami: each petal controller shows "pedal_NULLctrl_01 driven (translateY ← Head_Settings_Ctrl.Petal_Translate × 0.2, rotateX ← Petal_Rotation × 8)". The two "not transferred" warnings are gone, and the pose check gained two petal-slider probes (292 poses in total).

Limits

  • Moved pivots on a driven group are reported: the group turns about its origin.
  • Driven scale is reported, not transferred.
  • Matrix-placed groups are reported.

Materials

Murakami's flat lambert colours, carried over so the character is coloured in Unreal the way it looks in Maya.

Maya: tested (FBX round trip)Offline: testedUnreal: not run yet

What it is in Maya

Six plain lambert materials. Some meshes mix materials on different faces (the head material is also on part of GEO_Body). The swatches below are computed from the real values in the scene.

The challenges

  1. Unreal's importer creates materials, but the colours aren't faithful, for two reasons we confirmed in the scene:
    • The diffuse multiplier. A lambert's visible colour is color × diffuse, and diffuse defaults to 0.8 (all of Murakami's are 0.8). Taken at face value, the colour can come out 25% too bright.
    • Colour management. Murakami's scene uses Maya's colour management with the ACEScg rendering space, the default in recent Maya. The stored numbers are ACEScg; Unreal works in linear sRGB. Copied as-is, the colours shift, saturation especially.
  2. Different shader types store their colour differently. Lambert, blinn and phong use color × diffuse; standardSurface and aiStandardSurface use baseColor × base.
  3. A Maya quirk. When you reassign all of a mesh's faces to a new material, Maya keeps an empty link to the old one. Our first version listed Maya's default shader on a mesh that no longer used it.
  4. A trap with the blendshape meshes. The hidden blendshape target meshes go into the FBX too. Leaving them out looked like a clean-up, but it broke the blendshape names.

How we solved it

SOLUTION 1

Export the colour you actually see, in Unreal's colour space

For each material really used by an exported mesh, the exporter writes the shader type, the colour and its weight, and Maya's rendering space. Then it computes the colour Unreal needs:

  1. multiply by the weight (diffuse or base);
  2. convert with the standard ACEScg → linear-sRGB matrix. Linear Rec.709 is copied as is; an unknown colour space is reported.

Pick a material to see each step with its real numbers.

SOLUTION 2

A small table of shader types

Each shader type is looked up in a table that says which attribute holds the colour and which holds its weight. Adding a new shader type means adding one row.

SOLUTION 3

Check real membership, not leftover links

Instead of trusting every link from a mesh to a material, we ask Maya which faces or meshes are actually members of each material's shading group. Empty leftover links are ignored.

SOLUTION 4

Keep the blendshape target meshes in the FBX

I tried leaving the hidden target meshes out. The FBX round-trip test then showed that without them the FBX keeps the blendshape but loses the target names: weight[0] instead of Head_BS_Smile. Unreal names its morph targets from those names.

So they stay in the export, the reason is written in the code, and the test now guards it.

SOLUTION 5

One master material, one instance per Maya material

These are lambert materials, so the master M_KotsudoLambert is simple: a BaseColor parameter, fully rough, no shine. Each Maya material becomes a material instance of it with its colour, assigned to the skeletal mesh slot of the same name. Re-running updates the instances in place.

This runs as its own step after the rig build. A failure there is logged and never breaks the rig.

SOLUTION 6

Match slots by name, from strict to loose

Unreal names the mesh's material slots after the Maya materials, but sometimes changes the case or adds a suffix like _001. The match tries exact first, then case-insensitive, then "starts with", and takes the longest name that fits.

How we know it works

  • In Maya (tests/maya_materials_test.py): lambert with diffuse 0.5, standardSurface with base 0.7, and blinn; per-face assignments; textured and transparent materials reported; the conversion keeps white white; a real FBX export and re-import keeps the material names and the blendshape target names.
  • Offline: the slot-name matching.
  • On Murakami: the Checks tab lists "6 material(s)", all ACEScg, no problems.

Limits

  • Only flat colours. Textures, transparency, emission and shininess aren't transferred yet; they're listed in Checks.
  • The slot names have to match the Maya material names. Unreal's importer does that by default.
  • Found while building this page: saturated ACEScg colours fall outside sRGB. Murakami's orange and red come out with a red value above 1 (1.14 and 1.27). Unreal's base colour clamps at 1, so they should still look right, but this is worth checking on the first Unreal build.

Custom attributes

The animator's knobs: user-made sliders and switches on controllers. They do nothing by themselves; what matters is what they drive.

Maya: testedOffline: testedUnreal: channels built, new links not run yet

What it is in Maya

Examples on Murakami and the test rigs:

  • IK_FK on the limb switches;
  • BS_Smile and the other face sliders on head_ctrl;
  • Wink and Eyelid_UP on the eyes;
  • Petal_Translate and Petal_Rotation on Head_Settings_Ctrl;
  • a "Space" enum on a space-switch controller.

Not every extra attribute is a knob. Nodes also carry internal ones: our own rigTag_* tags, the manifest text, FBX bookkeeping.

The challenges

  1. Knowing which attributes are animator knobs, among all the internal ones.
  2. Unreal has no "extra attribute on a control". The closest equivalent is an animation channel: a float that lives under a control and shows up in the Details panel, the Anim Outliner and Sequencer.
  3. Knowing what each attribute drives, and rebuilding that link. An attribute can drive an IK/FK blend, blendshape weights, constraint weights or group channels, through any chain of maths nodes.
  4. Attributes that drive things we don't transfer shouldn't disappear silently.
  5. Attributes on controllers that belong to no module (the settings controllers).

How we solved it

SOLUTION 1

Export animator-facing attributes only

An attribute is exported when it is keyable or visible in the channel box, of a known type (float, int, bool, enum), and not an internal name. Each one carries its type, default, current value, min/max and enum labels.

SOLUTION 2

Each one becomes an animation channel on the same control

In Unreal, each exported attribute becomes an animation channel on the matching control, with the same limits and default. You select the control and the slider is there.

SOLUTION 3

One mechanism rebuilds every link

The walker (see the demo at the top) describes what each attribute drives as maths. Unreal rebuilds it with float nodes feeding one of four kinds of target.

SOLUTION 4

Anything else is reported

The Checks tab follows every slider downstream. If it moves a joint or group through a node network we don't transfer, it says so. That's how the petal sliders were found. Now that they're transferred, the warning is gone.

SOLUTION 5

Settings controllers and pose probes

Sliders on controllers that belong to no module are handled by the settings controllers (offset groups, solution 8).

The pose check then probes them: every custom slider is moved to its limit, and every enum to each value. Unreal must produce the same joints and the same blendshape weights as Maya. Murakami has 292 test poses.

How we know it works

  • tests/maya_blendshape_drivers_test.py: 12 wiring types (multiply, divide, power, add, reverse, clamp, remap, driven keys, conditions, chains), plus driven rotate and translate channels in centimetre and metre scenes. The walker's description, replayed, gives Maya's value.
  • tests/offline_blendshapes_test.py: the Unreal float graph, evaluated with numbers, matches the same reference, including the compare fallback.
  • Maya stores some utility results in 32-bit floats, so the tests allow a 0.0001 difference.

Limits

  • Unreal's channels are all floats for now. An enum works by number (0, 1, 2). Its labels are in the manifest and shown in the tool, but not on the Unreal slider. Unreal's integer or enum control types would be the improvement.
  • Bool attributes also become 0–1 float sliders.

Not yet run in Unreal

Everything above is checked against Maya and offline. These Unreal functions are used for the first time.

  • the compare and select nodes;
  • the Rotation and Position constraints;
  • the quaternion and vector nodes;
  • creating materials and material instances, and assigning slots.

If one has a different name in Unreal 5.6, the log names it, and that part falls back without breaking the build.
