Kotsudo Explained

How the Maya → Unreal Engine 5.6 rigging pipeline rebuilds each rig feature: the logic, the problems we hit, and how we solved them. Test character: Murakami.

Every feature follows the same five parts: what it is in Maya, the challenges, how we solved it (with a visual beside each solution), how we know it works, and its limits. Sliders and buttons in the figures are live: try them.

Maya side Unreal side A problem, or an old behaviour we replaced

The idea behind it all

The tool never asks "is there a node called X?". It asks "what moves what, and by how much?", writes the answer down in neutral terms, and lets Unreal rebuild it with its own tools.

  1. Read the evidenceLook at what the scene actually does, not at node names.
  2. Describe intentUnreal axes, centimetres, linear colours, maths steps. Not a list of Maya nodes.
  3. Rebuild nativelyUse Unreal's own Control Rig nodes and assets.
  4. Measure parityEach feature has a test comparing our description with what Maya computes.
  5. Never guess silentlyAnything we cannot describe is reported with its reason.

The shared walker: slider → maths → target

Three of the four features below rest on one piece of code. In Maya, a value is often computed from a slider through a chain of utility nodes (multiply, reverse, condition, driven keys and so on). The walker starts at the value and walks backwards to the slider, writing each step down as a simple operation. Unreal rebuilds that list with its float nodes. The same walker serves blendshape weights, space weights and driven groups.

Pipeline and manifest

How a Maya rig travels to Unreal: one FBX carries the skeleton, the mesh and a description of the rig, and Unreal rebuilds the rig from that description.

Maya: testedUnreal: in use (21/21 modules within T1)

What it is in Maya

The artist tags joint chains as modules with the tagger tool (an arm, a spine, a petal). A module is one rig setup on one joint chain. There are four module types:

TypeWhat it isMurakami modules
FKChainone controller per jointNeck, L_LegLeafToe, 2 eyes, 12 petals
IKFKSwitch3-joint limb with IK, FK and a switchL/R arm, L/R leg
SplineIKjoints following a curveSpine
IKLimbIK only, any lengthnone

Murakami has 21 modules. The export button writes three things: the FBX (skeleton and mesh) with the rig description inside it, one small FBX per controller shape, and a file of test poses.

The challenges

  1. An FBX only carries joints, meshes and skin. Controllers, constraints, IK handles and sliders don't survive the trip.
  2. Maya and Unreal disagree on axes and units. Maya is Y-up and right-handed; Unreal is Z-up, left-handed and in centimetres. Murakami's scene is in metres.
  3. Maya's own commands mix units. xform -matrix always answers in centimetres, but translation and pivot queries answer in scene units (metres here). Mixing them made some offsets 100× wrong.
  4. A controller doesn't have to sit on its bone. Petals and the chest rotate around custom pivots away from the joint.
  5. Control Rig can't draw a Maya curve. Controller shapes are NURBS curves in Maya; Control Rig draws meshes.

How we solved it

SOLUTION 1

A manifest travels inside the FBX

The exporter writes a JSON description of the rig, the manifest, into an attribute on the root joint (rig_manifest_json). The FBX carries that attribute as metadata, so one file holds everything. In Unreal, run_rig_builder.py reads it back from the mesh metadata.

Click a part of the manifest to see what it holds.

SOLUTION 2

Convert once, on the Maya side

Every position and direction is converted before it is written:

  • a Maya vector (X, Y, Z) becomes (X, Z, Y) in Unreal;
  • rotations get the same swap, exactly as the FBX importer converts joints;
  • lengths are converted to centimetres using the scene's unit.

The unit mix-up got its own guard: the manifest's schema check refuses a file where the two encodings of a controller offset disagree in length. A unit error can no longer move a control silently.

SOLUTION 3

Controls sit at the Maya pivot; a hidden null sits on the bone

Each controller record stores its origin: the rotate pivot, the point the animator rotates around. Unreal creates the control there. When that isn't on the bone, a hidden driver null (<control>_Drv) is parented under the control and placed exactly on the bone. The rig reads the null, so the bone follows the control with a fixed offset.

Rotate the petal control: the bone turns around the control's pivot, as in Maya.

SOLUTION 4

Curves become thin tube meshes

The exporter samples each NURBS curve into points (in Unreal axes and centimetres), builds a thin square tube around them, and saves one small FBX per shape. In Unreal those meshes go into a shape library, and each control uses its own.

The shape id is a hash of the geometry, so identical shapes are shared. If a shape can't be imported, a stock circle, box or sphere is picked instead.

How we know it works

  • The pose check's calibration compares every joint and control at rest with Maya. A conversion error (axes, units) would show on most joints at once.
  • On Murakami, every control sits within 0.013 cm of its Maya pivot, and 95% of joints at rest are within 0.0003 cm.

Limits

  • The root joint has to be named root.
  • The manifest's schema file doesn't describe the newest sections yet (blendshapes, rest pose, group stacks, spaces, settings controls, materials). The builder reads them, but the schema check doesn't validate them.

IK/FK limbs

Arms and legs the animator can pose two ways: joint by joint (FK) or by placing the hand or foot (IK), with a switch to blend between them.

Unreal: pose check, 4/4 limbs within T1

What it is in Maya

Three bound joints per limb (shoulder, elbow, wrist; or hip, knee, ankle). Two helper chains drive them: an IK chain with an IK handle and a pole vector, and an FK chain with one control per joint. The bound joints copy the helpers' local values through pairBlend nodes, weighted by the switch attribute IK_FK.

FK (forward kinematics): you rotate each joint yourself. IK (inverse kinematics): you place the end, and a solver works out the joint angles. The pole vector says which way the elbow or knee points.

Facts we measured in Maya, not assumed: the wrists and ankles don't turn with the IK controls; the knee stays exactly in the hip / foot / pole plane; and Murakami's arms and legs are perfectly straight at rest.

The challenges

  1. FK mode must really be FK. An early design left the IK solver running in FK mode, so moving one FK control made the whole limb react.
  2. The end bone's rotation. We first assumed Maya's wrists follow the IK control. They don't.
  3. Which parent does the limb ride on? Maya blends the chains locally, so the hip rides on the spine joint, not on the pelvis control above the FK chain.
  4. Straight limbs are hypersensitive. On a straight leg, a tiny change of reach moves the knee by centimetres. The knee was 3.16 cm off on chest poses.
  5. Small API traps. The Set Rotation node's input pin is called "Value", not "Rotation", so the end bone's rotation was silently not applied.

How we solved it

SOLUTION 1

The switch drives the solver's weight

The FK controls always write the full FK pose first. Then Control Rig's two-bone IK solver ("Basic IK") runs, and its Weight is the switch: at 0 it leaves the FK pose untouched, at 1 the limb is pure IK, in between it blends each bone's rotation.

Try it: move the IK target, bend the FK shoulder, and slide the blend.

SOLUTION 2

Measure the end bone, and export what Maya does

The exporter measures whether the end joint follows the IK control and writes it as a flag (ik_end_orient). On Murakami it doesn't, so in IK the wrist keeps its rest local rotation. The rotation is wired to the node's real "Value" pin, with a fallback.

SOLUTION 3

Root rebase: ride on the right parent

Maya blends the chains locally, so the hip rides on its parent joint (the spine), not on the FK control's parent (the pelvis control). The FK pose is therefore taken relative to the FK control's parent, then re-applied under a null that follows the hip's real parent bone.

SOLUTION 4

Fixed bone lengths, and an honest score for straight limbs

On a nearly straight limb, the middle joint's distance from the root–tip line is about h ≈ √(2·k·slack), where k = A·B/(A+B) from the two bone lengths and slack = A + B − reach. A tiny slack moves the knee a lot.

Two fixes: the solver uses the rest bone lengths instead of measuring them each frame, and the spine's tiny rest error was removed (see rest correction). The knee went from 3.16 cm to 0.15 cm. The pose check then scores the middle joint only on the error the limb's reach and the file precision can't explain.

Move the slack: the curve is for Murakami's arm (two 350 cm bones).

How we know it works

  • The pose check probes every FK control in FK mode and every IK control in IK mode, plus random mixed poses. All four limbs are within T1.
  • Hands, feet, shoulders and hips match Maya; the elbows and knees match once the straight-limb effect is accounted for.

Limits

  • The IK/FK module takes exactly three joints. Longer chains are refused with a clear message (the plain IK module still handles any length with FABRIK).
  • Maya's stretchy IK isn't detected yet, so the solver's stretch option stays off. Soft IK isn't transferred.

Spline IK

Joints that follow a curve, shaped by a few controls. Murakami's spine.

Unreal: pose check within T1 (worst 0.056 cm)

What it is in Maya

A spline IK handle on Spine1–Spine4. The curve's control points (CVs) are skinned to three hidden helper joints, each riding under an animator control: Pelvis_IKctrl, spine_ctrl_01, chest_ctrl. Moving a control pulls its CVs, the curve bends, and the joints slide along it. Spine4 is also orient-constrained to the chest. Murakami's spine doesn't stretch.

The challenges

  1. Each CV is pulled by several controls with skin weights. Our first version kept only the two strongest influences, so the spine bent differently from Maya.
  2. Stretch. The Unreal fit defaulted to stretching, while Murakami's spine keeps its length.
  3. The fit is an approximation. Unreal's "Fit Chain on Spline Curve" lands about 0.04 cm from the bind pose. Small, but it lifted the hips and broke the straight knees (see IK/FK).
  4. The control isn't the helper joint. The chest control was drawn 0.59 cm away from its Maya pivot because it was placed at the hidden helper joint.

How we solved it

SOLUTION 1

Each CV is the weighted average of all its controls

For every CV, Unreal creates one invisible point per influencing control, riding on that control. The CV's position is their weighted average with Maya's weights, built as a chain of lerps (blends).

Then Spline From Points builds the curve, and Fit Chain on Spline Curve places the bones along it, each keeping its length.

Move the controls, and compare "all influences" with the old "two strongest".

SOLUTION 2

Stretch only when Maya stretches

The exporter checks whether Maya's spline stretches and writes stretch_enabled. The fit uses alignment "Front" (bones keep their length), or "Stretched" only when Maya stretches.

SOLUTION 3

A rest correction cancels the fit's approximation

After the fit, each spine bone is re-applied as RestOffset × solved. The builder measures that offset itself right after compiling (see rest correction). Largest offset found on Murakami: 0.0379 cm.

The control itself is placed at the animator control's pivot (ue_control_origin), not at the helper joint. The curve isn't affected, because the CV points are placed from the CVs.

How we know it works

  • The spine is within T1 on every pose. The largest remaining error is 0.056 cm on Spine3 when the spine controls rotate: Unreal's fit approximating Maya's curve.
  • The chest control now sits on its Maya pivot (was 0.59 cm away).

Limits

  • No spline twist (roll distributed along the spine) yet.
  • Ribbons (surface-based spines) aren't supported.

Constraints and follow spaces

Bones and controls that follow something other than their parent: a constraint on a bone, or a controller whose group is driven by another part of the rig.

Unreal: pose check within T1

What it is in Maya

  • Constraints on bones: point, orient, scale or parent constraints (Spine4 orient-constrained to the chest, FK joints parent-constrained to their controls).
  • Follow spaces: a controller's group is moved by a constraint, a matrix or driven keys. Its Maya parent then isn't what really carries it. The petals ride on the head this way.

Space switching (a choice between several targets) is covered in its own section.

The challenges

  1. Where does Maya keep the offset? A maintained offset lives in the constrained node's parent space. Unreal's plain constraint nodes keep it in world space, and the bone drifts as soon as its parent rotates.
  2. Finding the real targets. The IK/FK switch's weight input is also connected under the constraint's target list, so it was counted as a target. And the helper IK/FK joints sit at the same positions as the real ones. Result: the toe control followed the knee.
  3. Feedback loops. A petal's follow space pointed at a bone the petal drives itself, so it chased itself and flew away when the head rotated.
  4. Some chains aren't plain FK. When the constraints can't be expressed as "control drives bone", the FK module has to do something else.

How we solved it

SOLUTION 1

Use the "Local Space Offset" constraint variants

Maya constraints become Control Rig constraint nodes with maintain offset, using the variants that keep the offset in the parent's space, as Maya does.

Rotate the parent: the world-space version drifts away from the parent; the local version stays attached.

SOLUTION 2

Read targets from the right plug, prefer real joints

Targets are read only from the constraint's targetParentMatrix inputs, which only real targets feed. When looking for the joint a target sits on, module joints are preferred over helper joints at the same position.

SOLUTION 3

A follow-space null, updated at the right moment, never in a loop

For a driven group, the exporter finds the joint the constraint's targets sit on (parent_space_bone). Unreal creates a null that follows that bone's solved transform and puts the control under it. The null's update runs right after the module that drives that bone.

If that bone is one the control drives itself, the space is replaced with the driven bone's parent, which breaks the loop. A warning is logged when a space follows a bone no module drives.

SOLUTION 4

Constraint mode for chains that aren't plain FK

When a chain's Maya constraints can't be expressed as "each control drives its bone", the FK module switches to constraint mode: it rebuilds each exported constraint as a Control Rig constraint node instead. The artist can also turn constraint detection off per joint (rigTag_skipConstraintDetection).

How we know it works

  • The toe follows its real targets; the petals follow the head; Spine4 follows the chest. All within T1 on the pose check.

Limits

  • Aim constraints and pole-vector constraints outside IK limbs aren't rebuilt.
  • Matrix-based constraints (offsetParentMatrix, blendMatrix) are reported, not rebuilt.

Rest correction

Making Unreal's rig start from exactly the pose Maya's rig rests in, even when the skeleton was imported in a slightly different pose.

Unreal: in use (95% of joints within 0.0003 cm at rest)

What it is in Maya

A skinned mesh remembers the bind pose: where the joints were when the skin was attached. The rig usually rests in that same pose, but not always. On Murakami the four toe joints were bound 1.0114 cm lower than where the rig keeps them (the foot FK control carries a −1.0114 translate).

The challenges

  1. Unreal's skeleton is the bind pose, not the rig's rest pose. The toe and its control sat 1 cm off at rest, and rotating the control swung the toe around the wrong point.
  2. Solvers don't land exactly on rest. The spline fit lands about 0.04 cm off. On a straight leg that tiny error became 3 cm at the knee.
  3. No absolute axis convention can be assumed. The FBX importer gives each bone its own fixed axis difference.
  4. An API gap. Unreal 5.6's Python Quat has no inverse(), which crashed the first try.

How we solved it

SOLUTION 1

Export both poses, move bones onto Maya's rest

The exporter writes rest_pose: for every joint, its current frame and its bind frame (read from the skin cluster). Before building any module, the builder moves each bone that differs onto Maya's rest:

  • position: the exported rest position;
  • rotation: the change "rest × bind⁻¹", applied on top of Unreal's own bone rotation. Only the difference is used, so no axis convention is assumed.

The log says which bones moved. The quaternion maths is plain Python, which avoids the missing inverse().

SOLUTION 2

Bake the solvers' rest error back into the graph

Right after compiling, the builder runs the rig at rest, measures each spine bone (offset = bind × solved⁻¹), writes those offsets into the graph, and compiles again. From then on the spine sits exactly on rest, and the knees stop paying for the spine's error.

How we know it works

  • Pose check calibration: no joint off at rest; 95% within 0.0003 cm (was: toe 1.01 cm, 95% within 0.038 cm).
  • The toe went from 1.01 cm off at rest to T0.

Limits

  • Rest correction is baked for the spine. Other solvers that land off rest would need the same treatment; none does on Murakami.

Custom attributes

The animator's knobs: user-made sliders and switches on controllers. They do nothing by themselves; what matters is what they drive.

Maya: testedOffline: testedUnreal: channels built, new links not run yet

What it is in Maya

Examples on Murakami and the test rigs:

  • IK_FK on the limb switches;
  • BS_Smile and the other face sliders on head_ctrl;
  • Wink and Eyelid_UP on the eyes;
  • Petal_Translate and Petal_Rotation on Head_Settings_Ctrl;
  • a "Space" enum on a space-switch controller.

Not every extra attribute is a knob. Nodes also carry internal ones: our own rigTag_* tags, the manifest text, FBX bookkeeping.

The challenges

  1. Knowing which attributes are animator knobs, among all the internal ones.
  2. Unreal has no "extra attribute on a control". The closest equivalent is an animation channel: a float that lives under a control and shows up in the Details panel, the Anim Outliner and Sequencer.
  3. Knowing what each attribute drives, and rebuilding that link. An attribute can drive an IK/FK blend, blendshape weights, constraint weights or group channels, through any chain of maths nodes.
  4. Attributes that drive things we don't transfer shouldn't disappear silently.
  5. Attributes on controllers that belong to no module (the settings controllers).

How we solved it

SOLUTION 1

Export animator-facing attributes only

An attribute is exported when it is keyable or visible in the channel box, of a known type (float, int, bool, enum), and not an internal name. Each one carries its type, default, current value, min/max and enum labels.

SOLUTION 2

Each one becomes an animation channel on the same control

In Unreal, each exported attribute becomes an animation channel on the matching control, with the same limits and default. You select the control and the slider is there.

SOLUTION 3

One mechanism rebuilds every link

The walker (see the demo at the top) describes what each attribute drives as maths. Unreal rebuilds it with float nodes feeding one of four kinds of target.

SOLUTION 4

Anything else is reported

The Checks tab follows every slider downstream. If it moves a joint or group through a node network we don't transfer, it says so. That's how the petal sliders were found. Now that they're transferred, the warning is gone.

SOLUTION 5

Settings controllers and pose probes

Sliders on controllers that belong to no module are handled by the settings controllers (offset groups, solution 8).

The pose check then probes them: every custom slider is moved to its limit, and every enum to each value. Unreal must produce the same joints and the same blendshape weights as Maya. Murakami has 292 test poses.

How we know it works

  • tests/maya_blendshape_drivers_test.py: 12 wiring types (multiply, divide, power, add, reverse, clamp, remap, driven keys, conditions, chains), plus driven rotate and translate channels in centimetre and metre scenes. The walker's description, replayed, gives Maya's value.
  • tests/offline_blendshapes_test.py: the Unreal float graph, evaluated with numbers, matches the same reference, including the compare fallback.
  • Maya stores some utility results in 32-bit floats, so the tests allow a 0.0001 difference.

Limits

  • Unreal's channels are all floats for now. An enum works by number (0, 1, 2). Its labels are in the manifest and shown in the tool, but not on the Unreal slider. Unreal's integer or enum control types would be the improvement.
  • Bool attributes also become 0–1 float sliders.

Blendshapes

Face shapes (smile, open mouth, eyelids) driven by sliders on the controllers. In Unreal they're called morph targets.

Maya: testedOffline: testedUnreal: not run yet

What it is in Maya

A blendshape node mixes a base mesh with target meshes: each target has a weight from 0 (base) to 1 (full target). Murakami has 10 targets on 3 nodes: four on the face (Smile, Omouth, CloseMouth, Disgusting) and three per eye. Sliders on the controllers drive the weights, through a multiplyDivide node set to × 0.1.

The challenges

  1. The FBX carries the shapes but not the wiring. Unreal imports the morph targets, but nothing moves them.
  2. The wiring varies: direct connections, multiply nodes, reverse, remap, driven keys, chains of them.
  3. Several meshes, several nodes. The artist must choose which blendshapes and which targets go to Unreal, and see it in the tool.
  4. Sensitivity. Without the × 0.1, a 0–10 slider reaches full weight after one unit, so the shape "explodes" at the start of the slide.

How we solved it

SOLUTION 1

Register blendshapes in the tool

The tagger's Blendshapes tab lists every blendshape node and its targets, with the driver and the maths found for each. The artist ticks what goes to Unreal. The choice is stored on the blendshape node itself (rigTag_exportBlendshape, rigTag_excludedTargets), so it travels with the scene.

SOLUTION 2

The walker describes the wiring

For each registered target, the shared walker follows the weight back to its slider and writes the maths. In Unreal each target gets: Get channel → float nodes → Set Curve Value. A morph target follows the animation curve of the same name, so writing the curve moves the shape. Missing curves are added.

Move the slider to see the × 0.1 at work, and switch it off to see why it's there.

SOLUTION 3

The pose check compares curve values

The Maya poses record each blendshape weight, and the slider probes move each face slider to its limit. Unreal must produce the same curve values within 0.001. A target with no curve in Unreal is reported by name, and the tool shows the result per target.

SOLUTION 4

Keep the target meshes in the FBX

Without the hidden target meshes, the FBX loses the target names and Unreal can't name its morph targets. They stay in the export (see materials, solution 4).

How we know it works

  • tests/maya_blendshape_drivers_test.py: 12 wiring types, the walker's description replayed gives Maya's weight.
  • tests/offline_blendshapes_test.py: the Unreal graph evaluated with numbers matches.
  • tests/maya_tool_ui_test.py: registering, excluding a target and "Register All" in the real tool window.

Limits

  • Corrective shapes (a shape that fires from a joint angle) and in-between targets aren't supported yet.
  • Not run in Unreal yet: the curve creation and Set Curve Value pins are untested there.

Space switching

A controller follows a different thing depending on a choice: a hand that follows the World, the Chest or the Head.

Maya: testedOffline: testedUnreal: not run yetMurakami has none; tested on a synthetic rig

What it is in Maya

Riggers build it with three pieces:

  • an empty group above the controller (here hand_space_grp);
  • a constraint on that group, with one target per space;
  • a choice attribute on the controller, usually an enum called "Space", that turns one target's weight on and the others off.

A weight is how much a target pulls on the group: 1 means "follow it fully", 0 means "ignore it".

The challenges

  1. Every rigger wires it differently. Weights can be switched by condition nodes, driven keys, reverse nodes, separate float sliders, choice nodes or matrix nodes. Recognising one specific setup only works on rigs built that way.
  2. The wiring goes through the constraint itself. Maya adds a weight attribute on the constraint (chest_ctrlW1) that feeds the target slot. Our walker first stopped there and took the constraint for the controller.
  3. Targets aren't always controllers. A space can be a joint, a locator hidden under a joint, or a locator in the world.
  4. Each space has its own offset. Maya stores one offset per target, and they don't have to agree. On Murakami's toe, switching IK → FK moves it 1.011 cm in Maya itself. Unreal's "maintain offset" only remembers one.
  5. Not every space is a full parent space. Some take only the rotation (orient: "the head keeps looking where the body points") or only the position (point).
  6. Murakami has no space switch, so it couldn't be the test.

How we solved it

SOLUTION 1

Describe the weights as maths, not as nodes

For each target, the walker follows the weight back to the slider and writes the steps. A condition node becomes a comparison step ("1 if Space = 2, else 0"). Driven keys become their key list. Any wiring made of these steps works, in any combination.

Try it: pick a space, then bend the chest or turn the head. The hand follows only the thing its active space points to.

SOLUTION 2

Walk through the constraint's own weight attributes

When the walk lands on one of the constraint's attributes, it keeps going upstream until it reaches a real controller. A weight attribute that nothing drives counts as a constant.

SOLUTION 3

Say what each target follows

Unreal doesn't know Maya's locators. For each target we record the nearest exported thing it moves with: the nearest controller above it, else the nearest exported joint, else the world.

SOLUTION 4

Measure each space alone, in Maya

We don't predict per-space offsets. We measure them. The exporter tries values for the slider and reads Maya's actual constraint weights each time. When exactly one target is active, it records where the controller sits.

The values tried come from the enum's entries, the slider's limits, and the numbers that appear in the maths. It also records which value selects which space, and the enum labels, including enums with explicit values like Low=0:High=10.

SOLUTION 5

Rebuild it in Unreal with one null per space

A null is an invisible transform in the Control Rig. The builder makes:

  • one null per space, hung under its target and placed where Maya puts the controller under that space alone;
  • the matching Unreal constraint: Parent, Rotation or Position;
  • weights computed live from the enum channel with the shared float nodes. Comparisons use Unreal's compare and select nodes, with a pure-arithmetic fallback.

Because each null already sits at its measured pose, each space keeps its own offset. That answers challenge 4.

SOLUTION 6

Orient and point spaces keep the other half

For a rotation-only or position-only space, the space null hangs under the controller's real Maya parent. The constraint then only overrides one half, and the other half still follows the parent.

SOLUTION 7

No silent guess

Before, an undescribable space quietly fell back to "follow the joint nearest to the targets". Now the reason is written down ("driven by several constraints", "matrix network", "unsupported weight wiring") and shown in the Checks tab, the Setup rows and the Unreal log. The fallback still exists, but it's labelled.

SOLUTION 8

The pose check probes every space

An enum is now probed on every value, not just its maximum. Testing only the maximum would skip the middle spaces.

How we know it works

A test rig (tests/maya_space_switch_test.py) with the common setups:

  • an enum through condition nodes, with world, controller and joint targets, and one offset edited on purpose;
  • an enum through driven keys;
  • an orient-only float slider with a reverse node;
  • a matrix-driven space.

For every value, the exported weights equal Maya's. The edited offset is measured at exactly 2.0, and the matrix case is reported instead of guessed. On Murakami, the toe's IK/FK blend is now recognised as a two-space switch ("IK = L_LegIKctrl, FK = L_LegFKctrl_03").

Limits

  • Matrix-based spaces (offsetParentMatrix, blendMatrix) are reported, not rebuilt.
  • So are groups driven by several constraints at once.
  • "Switch without jumping" (snapping the controller so it stays in place when you change space) is an animation tool and isn't built yet.

Offset / zero groups

The empty groups above a controller. Some just hold the rest position. Others are moved by sliders, like Murakami's petals.

Maya: tested (0.0001 cm)Offline: testedUnreal: not run yet

What it is in Maya

Above almost every controller sit one or more empty groups (_grp, _offset, _zero…).

  • Zero groups hold the rest position, so the controller's own channels read 0 at rest. The animator can always zero a controller to get back to rest.
  • Driven groups are moved by something else: driven keys, an "auto" behaviour, or a settings slider.

On Murakami, the 12 pedal_NULLctrl_* groups are moved by Petal_Translate and Petal_Rotation on Head_Settings_Ctrl.

The challenges

  1. Telling the kinds apart. A group can be static, constraint-driven (that's a space), slider-driven, or placed by matrix nodes. Each needs a different answer.
  2. Unreal has no "group" between a parent and a control. It has an equivalent for static groups (solution 2), but not for moving ones.
  3. Rebuilding a moving group exactly means reproducing how Maya builds a local transform: translate, the rotate axis, the rotation in the group's rotate order (xyz, zxy…), and the joint orient when the group is a joint. All of it converted from Maya's axes to Unreal's.
  4. Static groups above the moving one still have to count, even though Unreal doesn't create them.
  5. A hidden unit trap. Maya stores rotations in radians and distances in centimetres internally, but shows degrees and scene units (metres on Murakami). The unit-conversion nodes Maya inserts work in the internal units.
  6. The slider's controller belongs to no module. Head_Settings_Ctrl isn't in any tagged module, so Unreal never built it, and its sliders didn't exist.

How we solved it

SOLUTION 1

Record and classify each controller's group stack

Each controller records the groups between it and its parent controller, nearest first. Each group gets one of four labels, and each label has its own treatment.

SOLUTION 2

Static groups = the Unreal control's offset

An Unreal control has an "offset transform" separate from its animatable value. That is exactly a zero group. The builder puts the full rest transform into the offset, so the control's channels read 0 at rest.

No extra null is needed. This part already worked; now it's identified and documented.

SOLUTION 3

Driven groups become real nulls, rebuilt every frame

A null is inserted between the parent and the controller. Every frame its local transform is rebuilt as L(channel values) ∘ C, read "apply C, then L":

  • L is Maya's own local-transform formula, fed with the current channel values.
  • C is a constant computed once at build time (solution 5).
  • The driven channels come from the sliders through the shared walker maths. The other channels keep their rest values.

Try the two petal sliders. The numbers on the right are what the null receives.

SOLUTION 4

L follows Maya's order, and the rotate order matters

Maya builds a local transform in a fixed sequence: rotateAxis, then the rotation in the group's rotate order, then jointOrient (joints only), then translate. We build L in that same sequence.

The rotate order is easy to underestimate. The same three angles give a different result in a different order, as the two gizmos show. Change the angles or the orders.

SOLUTION 5

Convert axes, and flip the angle sign

Maya is Y-up; Unreal is Z-up. A Maya vector (X, Y, Z) becomes (X, Z, Y) in Unreal. Swapping two axes is a mirror: Maya is right-handed and Unreal is left-handed.

A mirror reverses what "positive rotation" means. So a rotation by θ about a Maya axis becomes a rotation by −θ about the matching Unreal axis. Same physical turn, opposite sign.

SOLUTION 6

The constant C absorbs everything that doesn't move

C is computed once at build time. It absorbs the static groups above the driven one, and the difference between Maya's parent and the Unreal parent. It is chosen so that, with the rest values, the null lands exactly where Maya's group is.

For the curious: C = L(rest)⁻¹ ∘ G_rest ∘ U_rest⁻¹, where G is the group's world pose in Maya and U the Unreal parent's.

SOLUTION 7

One unit rule, applied everywhere

The maths always goes from the value the animator sees on the slider to the value the animator sees on the target. In those terms, Maya's hidden unit conversions between a plain number and an angle or distance do nothing, so we count them as "× 1".

Our walker first got this right only for plain numbers like blendshape weights. For a rotate channel it would have produced radians.

SOLUTION 8

Settings controllers are built on first use

The exporter finds controllers whose sliders drive exported things but which belong to no module, and writes them as settings_controls. Unreal builds such a controller the first time a driven group or blendshape needs its slider, under its real Maya parent.

SOLUTION 9

One entry point for every module

The groups are inserted inside the one function every module already uses to find a control's parent. FK, IK/FK, spline and constraint controls all get them, without touching each module.

How we know it works

  • Against Maya's own world matrices (tests/maya_driven_groups_test.py): driven groups with random rotate orders and rotate axes, a driven joint with jointOrient, under randomly rotated static groups, in centimetre and metre scenes. The predicted world pose matches Maya's within 0.0001 cm and 0.0001°.
  • The Unreal graph, evaluated offline (tests/offline_driven_groups_test.py): the quaternion, vector and float nodes, evaluated with numbers, give the same result as the Maya-checked maths.
  • On Murakami: each petal controller shows "pedal_NULLctrl_01 driven (translateY ← Head_Settings_Ctrl.Petal_Translate × 0.2, rotateX ← Petal_Rotation × 8)". The two "not transferred" warnings are gone, and the pose check gained two petal-slider probes (292 poses in total).

Limits

  • Moved pivots on a driven group are reported: the group turns about its origin.
  • Driven scale is reported, not transferred.
  • Matrix-placed groups are reported.

Materials

Murakami's flat lambert colours, carried over so the character is coloured in Unreal the way it looks in Maya.

Maya: tested (FBX round trip)Offline: testedUnreal: not run yet

What it is in Maya

Six plain lambert materials. Some meshes mix materials on different faces (the head material is also on part of GEO_Body). The swatches below are computed from the real values in the scene.

The challenges

  1. Unreal's importer creates materials, but the colours aren't faithful, for two reasons we confirmed in the scene:
    • The diffuse multiplier. A lambert's visible colour is color × diffuse, and diffuse defaults to 0.8 (all of Murakami's are 0.8). Taken at face value, the colour can come out 25% too bright.
    • Colour management. Murakami's scene uses Maya's colour management with the ACEScg rendering space, the default in recent Maya. The stored numbers are ACEScg; Unreal works in linear sRGB. Copied as-is, the colours shift, saturation especially.
  2. Different shader types store their colour differently. Lambert, blinn and phong use color × diffuse; standardSurface and aiStandardSurface use baseColor × base.
  3. A Maya quirk. When you reassign all of a mesh's faces to a new material, Maya keeps an empty link to the old one. Our first version listed Maya's default shader on a mesh that no longer used it.
  4. A trap with the blendshape meshes. The hidden blendshape target meshes go into the FBX too. Leaving them out looked like a clean-up, but it broke the blendshape names.

How we solved it

SOLUTION 1

Export the colour you actually see, in Unreal's colour space

For each material really used by an exported mesh, the exporter writes the shader type, the colour and its weight, and Maya's rendering space. Then it computes the colour Unreal needs:

  1. multiply by the weight (diffuse or base);
  2. convert with the standard ACEScg → linear-sRGB matrix. Linear Rec.709 is copied as is; an unknown colour space is reported.

Pick a material to see each step with its real numbers.

SOLUTION 2

A small table of shader types

Each shader type is looked up in a table that says which attribute holds the colour and which holds its weight. Adding a new shader type means adding one row.

SOLUTION 3

Check real membership, not leftover links

Instead of trusting every link from a mesh to a material, we ask Maya which faces or meshes are actually members of each material's shading group. Empty leftover links are ignored.

SOLUTION 4

Keep the blendshape target meshes in the FBX

I tried leaving the hidden target meshes out. The FBX round-trip test then showed that without them the FBX keeps the blendshape but loses the target names: weight[0] instead of Head_BS_Smile. Unreal names its morph targets from those names.

So they stay in the export, the reason is written in the code, and the test now guards it.

SOLUTION 5

One master material, one instance per Maya material

These are lambert materials, so the master M_KotsudoLambert is simple: a BaseColor parameter, fully rough, no shine. Each Maya material becomes a material instance of it with its colour, assigned to the skeletal mesh slot of the same name. Re-running updates the instances in place.

This runs as its own step after the rig build. A failure there is logged and never breaks the rig.

SOLUTION 6

Match slots by name, from strict to loose

Unreal names the mesh's material slots after the Maya materials, but sometimes changes the case or adds a suffix like _001. The match tries exact first, then case-insensitive, then "starts with", and takes the longest name that fits.

How we know it works

  • In Maya (tests/maya_materials_test.py): lambert with diffuse 0.5, standardSurface with base 0.7, and blinn; per-face assignments; textured and transparent materials reported; the conversion keeps white white; a real FBX export and re-import keeps the material names and the blendshape target names.
  • Offline: the slot-name matching.
  • On Murakami: the Checks tab lists "6 material(s)", all ACEScg, no problems.

Limits

  • Only flat colours. Textures, transparency, emission and shininess aren't transferred yet; they're listed in Checks.
  • The slot names have to match the Maya material names. Unreal's importer does that by default.
  • Found while building this page: saturated ACEScg colours fall outside sRGB. Murakami's orange and red come out with a red value above 1 (1.14 and 1.27). Unreal's base colour clamps at 1, so they should still look right, but this is worth checking on the first Unreal build.

Pose check

The answer key: the same control moves are applied in Maya and in Unreal, and every joint and blendshape weight is compared.

Unreal: in use (Murakami 21/21 within T1)

What it is

At export, Maya records a set of test poses (murakami.poses.json). After the build, Unreal replays each pose on the new rig and compares. The result is a verdict line, a report with per-module tiers, the worst poses, and a comparison with the previous run.

The challenges

  1. Which poses? Enough to exercise every control, but few enough to run quickly.
  2. Constant offsets. The importer gives each bone a fixed axis difference, and a joint misplaced at rest would add the same error to every pose.
  3. Controls with moved pivots (pole vectors, pelvis, chest) replayed wrongly when only their translate channel was copied.
  4. Measuring correctly. The petals showed a constant 0.14° that didn't exist: a measurement artifact.
  5. Straight limbs make the middle joint's error look huge when it isn't (see IK/FK, solution 4).

How we solved it

SOLUTION 1

Rest, one probe per channel, random poses

  • Rest, used for calibration.
  • Probes: every unlocked rotate/translate channel (+20°, +5 cm), every custom slider to its limit, every enum to each value. IK/FK limbs are set to the mode the control belongs to.
  • 12 random poses moving 4 controls each, with random IK/FK modes.

Each pose records every joint's world position and rotation, and every blendshape weight. Murakami: 292 poses.

SOLUTION 2

Compare motion from rest, after calibrating

The error is Unreal's motion from rest against Maya's motion from rest. A constant offset (an importer axis difference, a joint misplaced at rest) cancels out.

Calibration runs first: joints and controls at rest against Maya. It fails only when most joints are off (95th percentile above 0.1 cm), which means a conversion error. A few joints off are listed once as rest offsets.

Controls are replayed with their Maya world-matrix motion, which rotates about the pivot as Maya does.

SOLUTION 3

Tiers, and the right maths for angles

Each module gets a tier: T0 ≤ 0.01 cm / 0.01°, T1 ≤ 0.1 cm / 0.5°, otherwise "above T1".

The petal "0.14°" came from the maths. The poses file stores rounded quaternions (rotation records), and the angle was computed with acos, which turns tiny rounding into a visible angle near zero. Now the quaternions are normalised and the angle uses atan2. The petals became T0.

Move the rounding error: the true angle is always 0.

SOLUTION 4

A report that points at the fix

The Output Log ends with a VERDICT line, the module tiers, the five worst controls and what changed since the last run. The full report (HTML and JSON) sits next to the poses file:

  • worst poses list their three worst joints, so you see where a chain breaks;
  • "controls whose probe breaks the most" names the setup to fix;
  • each module is marked better, WORSE, mixed or same against the previous run;
  • near-straight limbs show raw and unexplained errors side by side.

How we know it works

  • Offline tests of the scoring, including a fake 0.3 cm error on a bent arm that still scores 0.299 (the straight-limb allowance doesn't hide real errors).
  • It found every bug in this document's earlier sections; each fix was confirmed by a better pose report.

Limits

  • The Unreal side drives a rig instance from Python; if the engine gives no fresh instance it uses the editor's own, reset before every pose.
  • Evidence so far comes from one character. A second rig would show what still depends on Murakami.

Graph layout

Making the generated Control Rig graph readable: nodes that don't overlap, grouped in named boxes, one per module.

Offline: testedUnreal: in use

What it is

The builder creates hundreds of nodes. Without layout they pile up on top of each other, and nobody can find the spine's nodes among the petals'.

The challenges

  1. Node sizes are unknown. The editor only knows a node's real size once it has been drawn.
  2. Wires should read left to right, with few crossings.
  3. Hundreds of modules' worth of nodes must stay findable.

How we solved it

SOLUTION 1

Columns follow the wiring

Inside a module, a node sits one column to the right of everything that feeds it. A node that only feeds others is pulled right, next to its first consumer, so getters sit beside the node they feed. Inside a column, nodes keep the order of their inputs, which reduces crossing wires.

Sizes are estimated from the title length and the number of visible pins, rounded up, with generous gaps, so a slightly short estimate never makes nodes touch.

SOLUTION 2

One named, coloured box per module

Each module's nodes are framed by a comment box named after the module ([RB] Spine), coloured by module type. Boxes stack downwards in build order, and a new column starts when the stack gets too tall. Blendshapes and shared nodes get their own boxes.

How we know it works

  • The layout maths is plain Python, so it runs without Unreal. It was checked that way when written (no overlaps, every node inside its box), but that check was lost with an old scratch folder: there is no test file in tests/ for it yet.
  • In Unreal, the generated graph shows one box per module.

Limits

  • Sizes are estimates, so spacing is generous rather than tight.

Tagger tool and Checks

The Maya window where the artist declares what each part of the rig is, checks what will transfer, and exports.

Maya: tested (offscreen UI test)

What it is in Maya

A window with three tabs, opened from the shelf:

  • Modules: tag joint chains (start and end bone, type, name), see each module's controllers and setup, and export.
  • Blendshapes: register blendshape nodes and targets (see blendshapes).
  • Checks: everything the export will and won't transfer, by severity.

The challenges

  1. Meaning can't be guessed reliably. Whether a chain is a limb or a tail is the artist's decision.
  2. Problems should show before export, not after a long Unreal build.
  3. Feedback from Unreal should come back to the place where the artist works.
  4. Maya caches old code: after an update, the shelf button ran the previous version, and no poses file was written.

How we solved it

SOLUTION 1

The artist declares the meaning; the tool finds the evidence

Tags are plain attributes on the joints (rigTag_moduleType, rigTag_moduleName, rigTag_startBone, rigTag_endBone, rigTag_role…). Everything else (controllers, constraints, spaces, sliders, groups) is found by reading the scene.

SOLUTION 2

Analyze Scene and the Checks tab

Analyze Scene runs the same analysis as the export, without exporting. Each module gets a Controllers branch (pivot, shape, space, groups) and a Setup branch (IK/FK switch, pole vector, curve points, constraints, spaces). The Checks tab lists errors, things to review, and notes, each with its reason.

SOLUTION 3

Unreal's verdict comes back into the tool

When a pose report exists next to the export, the tool shows each module's tier in a column, the verdict in a label, and blendshape results per target. Open Pose Report opens the HTML. The export fields (rig name, file name, folder) are remembered between sessions, and after export a summary lists modules, blendshape targets, controller shapes and test poses.

SOLUTION 4

The shelf button reloads the code

The launcher reloads the tool's modules and clears Python's import caches before opening, so an update is always picked up, including files added after Maya started.

How we know it works

  • tests/maya_tool_ui_test.py builds the real window without a screen on a copy of Murakami and checks the tabs, blendshape registration, Analyze Scene, the Setup rows, the Unreal report column, the export summary and the remembered fields.

Limits

  • Tagging is manual. A suggestion feature (proposing modules from the scene) would speed up a new character.

Not yet run in Unreal

The modules, constraints, rest correction and layout run in Unreal today (21/21 modules within T1). The newer features are checked against Maya and offline, and these Unreal functions are used for the first time.

  • the compare and select nodes;
  • the Rotation and Position constraints;
  • the quaternion and vector nodes;
  • creating materials and material instances, and assigning slots;
  • adding morph curves and the Set Curve Value node for blendshapes.

If one has a different name in Unreal 5.6, the log names it, and that part falls back without breaking the build.

On the next build, check four things: the character is coloured; Head_Settings_Ctrl's petal sliders open and twist the petals; the blendshape sliders change the face; and send the pose report.
